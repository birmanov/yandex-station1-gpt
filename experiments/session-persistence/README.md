# Эксперимент: сохранение входа в веб-пульт

> **Незавершённый снимок. Не развёрнут на устройстве, не является готовым или проверенным безопасным обновлением.**

Здесь отдельно сохранены текущий локальный кандидат `StationRemote.java` и тест `SessionPersistenceCheck.java`. Они не участвуют в обычной сборке `remote/build.py`. Общая зависимость `VlessLink.java` находится в `remote/src/`.

Цель: сохранять вход на 30 дней и восстанавливать сессии после перезапуска службы, не убирая пароль, CSRF и проверку Origin.

## Что известно о проверках

Предшествующая версия кандидата прошла базовые сценарии на Android, включая создание и восстановление входа в разных процессах. Проверены последовательные выход и смена пароля, отказ при неверном CSRF/Origin и закрытый режим при повреждённом хранилище.

Независимая проверка затем нашла блокирующие замечания:

- Гонка между сменой пароля, проверкой старого пароля и выдачей/сохранением сессии.
- Необходимость проверять результат ограничения прав на каталог и файлы с токенами.
- Несогласованность памяти и диска при ошибке записи отзыва сессии, которая может привести к её восстановлению после перезапуска.

## Доработка `2.0.0-local.2` (11 ноября 2026)

Все три замечания устранены в коде кандидата; **на устройстве это ещё не прогонялось**.

1. **Гонка смены пароля.** `setPassword` теперь берёт `sessionLock` (внешний) и затем `configLock` (внутренний), меняет поколение, очищает сессии и перезаписывает хранилище в одной критической секции. Вход возвращает поколение (salt), против которого проверен пароль, а `newSession(generation)` под `sessionLock` отказывает с 401, если поколение уже сменилось. `/api/password` проверяет текущий пароль, ротирует и выдаёт новую сессию под одним захватом `sessionLock`.
2. **Права на файлы.** `restrict()` снимает права для всех, выставляет только владельцу и проверяет результат каждого вызова; при неудаче запись отменяется. Права выставляются на пустой файл до записи токенов; каталог хранилища ограничивается до `0700`.
3. **Память и диск при ошибке отзыва.** Отзыв сначала применяется в памяти и никогда не откатывается. Если хранилище не перезаписать, устаревший файл удаляется (или усекается), ставится флаг `sessionStoreDirty`, и таймер повторяет сохранение примерно каждые 5 с. Если и удаление невозможно, ошибка возвращается клиенту, но сессия в памяти остаётся отозванной. Неудачная выдача сессии не оставляет её в памяти.

Этот снимок скомпилирован JDK 17 с `--release 7` вместе с тестами. Выполнение тестов на обычной JVM невозможно: конструктор требует Android `InputManager`.

### Режимы теста

```sh
# на Станции, из каталога с собранными классами для API 23
CLASSPATH=... app_process / SessionPersistenceCheck all
# или по отдельности: basic | rotation | login-race | write-failure | concurrent
# и межпроцессный: seed /data/local/tmp/remote-session-process-X, затем recover <тот же путь>
```

`write-failure` имитирует ошибку записи, подставляя каталог вместо `sessions.properties.new`; это контролируемая подмена в изолированном каталоге, а не настоящая порча файловой системы. Проверка POSIX-прав использует `android.system.Os.stat`; вне Android она пропускается с пометкой `SKIP`.

До выпуска нужны полный прогон всех режимов на устройстве и независимая проверка. Эксперимент нельзя автоматически подставлять вместо установленного сервера.

## Изоляция тестов

Тестовые пароли с префиксом `fixture-` — вымышленные данные, не пароль владельца. Тесты создают отдельные каталоги `/data/local/tmp/remote-session-*`. Нельзя менять их на каталог действующего пульта или читать реальные файлы авторизации для проверки.

Тест требует Android API и root-контекст для инициализации управления, а не только обычную настольную JVM. Перед запуском нужно отдельно собрать кандидат и тест для API 23, соблюдать ограничение памяти и закрыть тестовые процессы. На Android 6 использовать свежие имена JAR при изменении класса, чтобы не принять старый ART-кэш за ошибку исходников.
